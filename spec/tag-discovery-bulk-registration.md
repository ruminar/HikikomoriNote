# タグ発見・一括登録支援 仕様書

対象：ひきこもりnote／おしゃべりnote（次期バージョン向け）  
状態：実装依頼用仕様（既存コード調査後に実装詳細を決める）

## 0. Codexへの依頼

この仕様書を**最初から最後まで読んでから**、現行コード・画面・設定保存形式を調査し、実装方針を短く整理したうえで変更を始めてください。局所的にボタンを増やすだけでなく、**3つの入口が同一のタグ選択・一括登録体験に合流する設計**を優先します。

既存機能の破壊や大規模な再構築は避けてください。不明な点は現行実装に沿って判断し、判断理由と変更範囲を報告してください。2つの拡張機能が別リポジトリ／別ビルドの場合、作業対象リポジトリの範囲を確認し、他方の変更が必要ならその変更点を明確に切り分けてください。まず調査と実装計画、その後に実装・確認という順で進めてください。

## 1. 背景と目的

『ひきこもりnote』は、note運営のおすすめに依存せず、利用者が自分で作者・タグ・記事を選んで閲覧するための拡張機能です。お気に入りグループ1〜8には、タグ（`#...`）などを登録・移動・削除でき、不要になった項目は既存の管理画面で容易に整理できます。

今回の目的は、**新しいタグを発見したら気軽にまとめて取り込み、実際に読んでから必要に応じて整理できるようにすること**です。登録前にすべての記事を精査する必要はありません。

- 外部ChatAIや他の利用者が作った提案文から、タグをまとめて取り込める。
- 閲覧中の記事に設定されたタグから、関心のあるものをまとめて取り込める。
- 『おしゃべりnote』の既存チャットからも、AIの1件の回答に含まれるタグをまとめて取り込める。
- 既存の、お気に入りグループへの保存・移動・削除の仕組みを最大限利用する。

**LLMを『ひきこもりnote』に内蔵しないこと。** APIキー、LLM接続設定、外部サーバー、独自おすすめアルゴリズムは今回不要です。

## 2. 全体構成：3つの入口／1つの登録処理

```text
① ひきこもりnote：設定メニュー「タグ登録支援」
   ├─ 現在のお気に入りタグを使ったAI依頼プロンプトのコピー
   └─ 外部のAI・人間が作った提案文を貼り付け → 「確認」
                                      │
② ひきこもりnote：記事画面          │
   └─ 「記事タグを確認」 → 記事の実タグを取得 ─┤
                                      ├─ タグ候補の正規化・重複除去
③ おしゃべりnote：AI応答欄           │   ↓
   └─ 「まとめて確認」 → 当該応答から抽出 ───┘ 共通の一括登録ダイアログ
                                           ↓
                                  タグボタンでON/OFF選択
                                           ↓
                                  グループ1〜8から1つ選択
                                           ↓
                                  選択タグをまとめて追加
                                           ↓
                             既存のお気に入り管理画面で整理
```

「共通」は**UIと振る舞いの共通仕様**を意味します。実コードをライブラリ化するか、各拡張へ小さな共通処理を組み込むかは、既存のリポジトリ／ビルド構造を調べて適切に決めてください。拡張機能間で同じストレージを読めると仮定しないこと。

## 3. 入口①：ひきこもりnoteの「タグ登録支援」

### 3.1 画面の追加

設定画面の**左メニュー**に「タグ登録支援」を追加します。開くと以下を配置します。

1. タグ提案文の貼り付け用テキストエリア（自由文を入力可能）
2. 「確認」ボタン（貼り付けた文章からタグ候補を抽出し、一括登録ダイアログを開く）
3. 「タグ提案用プロンプトをコピー」ボタン（現在のお気に入りタグを使って外部ChatAI向けの依頼文を生成し、クリップボードへコピー）

### 3.2 AI向けプロンプト生成

- 現在のお気に入りグループ1〜8から、`#`タグの項目のみ抽出し、重複を除いてプロンプトに含めます。`@`作者や`&`記事など、タグではない項目は含めません。
- プロンプトには「既存のタグを参考に、noteで興味を持てそうな**新しい閲覧用タグ**を提案してほしい」「各候補を `[#タグ名]` の形式で出力してほしい」「実在するタグを優先してほしい」旨を明記します。
- コピーは**端末のクリップボードまで**。外部AIサービスへの自動送信はしません。
- お気に入りタグが0件でも、興味・関心を利用者が追記して使える汎用プロンプトを生成できるようにします。
- コピー成功・失敗は既存UIの通知方法に合わせて簡潔に知らせます。

**プロンプトの出力例（雛形）**

```text
私はnoteで読む記事を探すため、お気に入りのハッシュタグを増やしたいです。
現在登録しているタグ：［ここに実際のお気に入りタグ一覧］
これらを参考に、新しく試してみると面白そうなタグを提案してください。
できるだけnote上で実際に使われていそうなタグを優先し、
各候補を [#タグ名] の形で列挙してください。
既存のタグそのものを繰り返す必要はありません。
理由や補足説明を添えても構いません。
```

### 3.3 提案文の取り込み

ユーザーが次のような文字列を貼り付けた場合、候補として抽出します。

```text
[#マッチョ茶道][#半透明ハイキング][#不老不死デコポン]
```

これに加え、通常の `#タグ名` が文章中・改行区切りに含まれるケースにも対応します。タグの説明文を含む自然文を貼り付けられますが、**自然言語による意味推論は不要**です。明示されたハッシュタグ表記だけを抽出します。

## 4. 入口②：記事画面の「記事タグを確認」

- 記事画面で既存の「記事全文を取得」ボタンの**直下**に「記事タグを確認」ボタンを設けます。既存ボタンの所属拡張・挿入位置は、実際のコードで確認してから変更してください。
- ボタンを押すと、**現在開いている記事に実際に設定されたタグ**を取得し、共通の一括登録ダイアログに表示します。
- 記事にタグが1件しかなければ1件だけ表示します。タグがないときは簡潔にその旨を通知します。
- タグは記事のタグ表示・対応するリンク等を根拠として取得します。**本文中に書かれた `#` 付き文字列を記事タグと誤認しない**こと。
- 「この記事が参加している募集」、おすすめ記事、関連カード、他の著者の情報など、**記事に設定されたタグではないものを混入させない**こと。
- 追加の外部API呼び出しは原則不要。既存のnoteページ上の情報を利用し、DOM変更への耐性を考慮して取得箇所を限定してください。

## 5. 入口③：おしゃべりnoteの「まとめて確認」

- チャットのAI回答にある既存の**「コピー」ボタンの左隣**に「まとめて確認」ボタンを追加します。
- クリックした**その回答1件の文章だけ**を解析します。別メッセージや会話履歴全体は対象にしません。
- 候補タグがあれば、①②と同じ一括登録UIを表示します。
- 既存のタグ単体クリックによる検索・登録機能、コピー機能は変更せず残します。
- ここから追加するタグが、現在の『おしゃべりnote』と『ひきこもりnote』で意図しているお気に入り保存先に正しく反映されるか、**既存の保存・共有方式を調べて検証**してください。拡張機能ごとにストレージが分離される場合、安易な共有前提で実装しないこと。

## 6. 共通の「タグをまとめて登録」ダイアログ

### 6.1 候補表示と選択

- タグ候補を、**タグ名そのものがON/OFFできるトグルボタン**として並べます。チェックボックスは使用しません。
- **初期状態はすべてOFF**。
- タグボタンを押すたびにON/OFFが切り替わります。ON状態は色・チェック印などで判別でき、キーボードでも操作できること（適切な `aria-pressed` など）。
- 「すべてON」「すべてOFF」のボタンを用意します。
- 選択数（例：`3 / 12件選択`）を表示します。
- 登録先は**お気に入りグループ1〜8から1つ**選択します。選んだタグはそのグループへまとめて登録します。
- 「選択したN件を登録」ボタンを設けます。N=0では押せません。
- 登録が済んだら、件数などの簡潔な結果通知を示します。登録直後に別途の確認手順を強制しないでください。

### 6.2 登録前の検索を必須にしない

この機能は**まず雑に登録し、記事を読んでから、既存のお気に入り画面で移動・削除する**使い方を想定しています。タグを一つずつ検索して内容を吟味するステップは不要です。検索リンク等を補助的に残す場合も、一括登録の動線を邪魔しないこと。

### 6.3 保存処理

- **既存のお気に入り登録ロジック・保存形式・グループ制約に従う**こと。
- 候補は正規化・重複除去し、同一のタグを二重登録しないこと。既存登録との重複も適切に扱ってください。
- `@作者`・`&記事`など他種類の既存登録を一切破壊しないこと。
- 既存の登録数制限などに達した場合、黙って既存項目を削除・上書きせず、保存できなかった件数を伝えること。
- ダブルクリック・連打で重複登録や状態競合を起こさないこと。
- 追加後のグループ移動・ドラッグ削除などは**現行UIをそのまま利用**します。新たなUndo・履歴管理は不要です。

## 7. タグ文字列の抽出・正規化

- 最優先で `[#タグ名]` の形式を確実に読み取ります。隣接していても、複数行でも取り込みます。
- 通常の `#タグ名` も取り込みます。文章中の説明や箇条書きが混在してもよい設計にします。
- タグ名の前後の余分な空白や括弧を除去し、登録形式は既存のお気に入りタグ表現に合わせます。
- 日本語・英数字・一般的なnoteのタグ文字列を扱えること。タグ名に使える文字・長さは既存仕様やnoteの実態を確認し、**独自の過剰な制約を作らない**こと。
- `# 見出し`（#の直後に空白）、URLの一部、Markdown構文、`@作者`、`&記事`を誤検出しないようにします。
- 抽出結果が0件なら、`[#タグ名]` 形式の例とともに簡潔に知らせます。
- 利用者や外部AI由来の文章は**非信頼入力**として扱い、タグ表示には安全なテキスト描画を使います。HTMLとして解釈・実行しないこと。

## 8. UI・実装の原則

1. ①②③は同じ一括登録体験とし、入口ごとに登録仕様を増殖させない。
2. 既存の画面レイアウト・デザインシステム・通知方法に合わせる。専用の大規模UI基盤は作らない。
3. 処理責務を、**タグ取得／抽出 → 正規化 → 選択UI → 保存**に分ける。
4. 外部AIのAPI連携、ネットワークスキャン、タグの自動評価、AI推薦の自動実行は対象外。
5. 自動お気に入り追加はしない。必ず利用者がON/OFFと登録先を決めて登録する。
6. 既存機能・設定移行・Android Firefoxでの利用可能性を壊さない。
7. 二つの拡張のソース構造が異なる場合は、**無理な共通ライブラリ化より、保守しやすい小さな共通仕様**を優先する。
